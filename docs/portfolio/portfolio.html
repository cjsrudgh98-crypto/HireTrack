OVERVIEW프로젝트 개요

취업 준비를 하면서 지원 현황을 스프레드시트·메모장·북마크에 나눠 적다 보니, 마감을 놓치고 어느 회사에 어떤 자소서를 냈는지 헷갈리는 일이 반복됐습니다. HireTrack은 공고 수집 → 지원 상태 관리 → 자기소개서 작성 → 결과 분석을 한 흐름으로 묶었습니다. 웹앱 · API 서버 · 크롬 확장 프로그램 · 캘린더 피드로 구성되고, 배포·백업·복구까지 실제 운영을 전제로 만들었습니다.

PROBLEM SOLVING기술적 도전과 해결

기능이 "돌아가는" 데서 멈추지 않고, 동시 요청 · 운영 DB · 보안처럼 실제로 쓰면 깨지는 지점을 테스트로 재현하고 막았습니다.

01동시 상태 변경으로 이력이 끊기는 문제

문제
같은 공고에 상태 변경 4건을 동시에 보내면 모두 같은 "이전 상태"를 읽어 이력이 전부 관심 → X로 기록됨. 통계가 이 이력으로 계산되므로 숫자가 틀어짐 (빠른 연속 드래그, 웹·확장 동시 사용)
해결
상태 변경 때 공고 행을 SELECT … FOR UPDATE 로 잠가 한 줄로 세움. 처음엔 H2 에서만 통과 — PostgreSQL 은 잠금 대기 뒤 잠근 행만 최신 값으로 다시 읽고 조인한 행은 옛 값을 쓰기 때문. 잠금 쿼리에서 join fetch 를 빼고 잠금 후 따로 읽도록 수정
결과
4개 스레드 동시 변경 테스트를 H2 · PostgreSQL 양쪽에서 실행, 이력 체인 끊김 0건 (수정 전 5회 중 5회)

02URL 추출 기능의 SSRF

문제
사용자가 넣은 URL 로 서버가 요청을 보내므로, localhost · 사설망 · 클라우드 메타데이터(169.254.169.254) 같은 내부 주소를 찌를 수 있음
해결
http/https · 80/443 만 허용, userinfo 거부, DNS 결과 IP 전부 검사(IPv4-mapped IPv6 · NAT64 포함), 자동 리다이렉트를 끄고 hop 마다 재검사. 시간·본문 크기 제한, 사용자별 분당 요청 제한
결과
로컬 HTTP 서버로 리다이렉트 우회까지 테스트 · 0x7f000001, 2130706433 같은 표기도 차단

03자소서 버전 동시 저장

문제
두 탭에서 같은 문항을 동시에 저장하면 같은 버전 번호가 두 번 생기거나, 다른 탭의 내용을 모른 채 덮어씀
해결
클라이언트가 본 baseVersion 검사 + (question_id, version) 유니크 제약의 두 겹. 자동 재시도 대신 409 를 돌려주고, 화면은 쓰던 내용을 지우지 않은 채 최신 버전과 비교해 보여줌
결과
5개 스레드 동시 저장 테스트(PostgreSQL 포함)에서 1건만 저장 · 나머지 409

04"현재 상태"로 세면 틀리는 통계

문제
현재 상태로 세면 면접까지 갔다가 떨어진 공고가 "불합격"으로만 잡혀 서류 통과율이 낮게 나옴. 결과 대기 중인 건을 분모에 넣으면 통과율이 실제보다 낮아짐
해결
상태 이력에서 공고마다 "도달한 가장 높은 단계"를 JPQL 로 집계. 결과가 나온 건만 분모에 넣고 대기 건은 따로 표시, 10분 안에 되돌린 변경은 제외
결과
퍼널 · 통과율 · 응답 기간이 실제 진행과 일치 · 통계 쿼리는 PostgreSQL 에서도 테스트
HireTrack · 포트폴리오6

05크롬 확장 프로그램의 최소 권한

문제
서버 요청 방식은 JS 로 그려지는 페이지·로그인이 필요한 페이지를 못 읽음. 그렇다고 확장에 <all_urls> 권한과 웹앱과 같은 토큰을 주면 유출 시 피해가 큼
해결
activeTab 만 써서 아이콘을 누른 탭만 읽고, 렌더링된 HTML 을 parse-html 로 보내 같은 파서 체인이 처리. 확장 전용 토큰(SCOPE_EXTENSION)은 추출·등록만 가능, CORS 는 고정된 확장 ID 하나만, 본문은 3MB 상한
결과
확장 토큰으로 목록 조회 시 403 · 다른 확장 출처는 CORS 거부 · 4MB 본문은 413 — 통합 테스트로 고정

06마감 알림 스케줄러의 중복 발송 · 시간대

문제
서버가 여러 대거나 스케줄러가 겹쳐 돌면 같은 메일이 두 번 나감. 서버가 UTC 면 D-day 가 하루 어긋남
해결
(posting_id, remind_day) 유니크 제약 + 발송 기록과 메일 발송을 한 트랜잭션으로 묶어 메일이 실패하면 기록도 롤백(다음 실행에 재시도). D-day 는 서울 날짜 기준, 사용자별로 하루 한 통에 모아 보냄
결과
동시 실행에도 1통 · 발송 결과는 hiretrack.reminders{result} 지표로 관찰

07H2 에서는 통과하고 PostgreSQL 에서 깨지는 쿼리

문제
목록 검색에서 null 파라미터를 PostgreSQL 이 bytea 로 추론해 varchar like bytea 오류(500). H2 테스트는 모두 통과해 배포 리허설에서야 발견
해결
cast(:x as String) 로 타입 명시. Testcontainers 로 모든 API 통합 테스트를 실제 PostgreSQL 에서도 돌리도록 서브클래스 추가, 스키마는 Flyway 로 관리하고 Hibernate 는 검증만
결과
같은 시나리오를 H2 · PostgreSQL 양쪽에서 실행 — 이후 동시성 버그(01)도 이 테스트가 잡음

08배포 리허설 · 자동 롤백 · 백업 복구

문제
배포 스크립트·백업이 "있기만" 하고 실제로 동작하는지 모름. 리허설에서 메일 미설정 시 헬스체크 DOWN → 배포가 매번 롤백, Nginx upstream 이름 충돌, 스크립트 CRLF 로 리눅스 실행 불가 발견
해결
운영과 같은 이미지·compose·스크립트로 로컬 리허설. 메일은 health 에서 제외(지표로 관찰), upstream 이름 변경, LF 통일 + .gitattributes. 헬스체크 실패 시 직전 이미지로 자동 롤백
결과
깨진 이미지 배포 → 자동 롤백 확인 · DB 볼륨 삭제 후 백업에서 복구한 데이터가 스냅샷과 완전히 동일

09추측으로 만든 파서를 실제 공고로 검증

문제
사이트 구조를 추측한 HTML 로 만든 전용 파서가 실제 공고에서 맞지 않음. 사람인은 본문을 JS 로 나중에 불러오는 껍데기, 잡코리아는 요약 표가 메타 설명 · JSON-LD 로 바뀌어 있었음
해결
껍데기에도 있는 og:title · 메타 설명("경력:… 마감일:…")을 항목 이름으로 읽도록 수정, 실제 구조를 따른 픽스처(내용은 가짜)로 테스트 고정. 자동화 차단은 우회하지 않음
결과
잡코리아 실제 공고 2/2 는 6개 항목 모두. 사람인 3/3 은 서버 요청으로 4개(근무지·고용형태 빈칸 안내), 실제 크롬의 확장 프로그램으로는 6개 모두
